# v4.5 acceptance / v4.5 验收

v4.5 turns the existing Trace and Contract core into a complete, reviewable
business regression example. The acceptance target is narrow: a developer can
run a normal refund case, inject known business defects, and see each defect
blocked with a useful rule and evidence path.

v4.5 将已有的 Trace 和 Contract 核心落成一个完整、可审核的业务回归案例。
验收目标很明确：开发者能够运行正常退款流程，注入已知业务错误，并看到规则和
证据路径对应的阻断结果。

## Acceptance matrix / 验收矩阵

| Check / 检查 | Expected result / 预期结果 |
| --- | --- |
| Normal refund / 正常退款 | exit `0`, all contract checks pass |
| Wrong order / 错订单 | exit `1`, relation/path/state differences |
| Excess amount / 超额金额 | exit `1`, amount relations and tool error |
| Skipped eligibility / 跳过资格检查 | exit `1`, required tool/path differences |
| Duplicate refund / 重复退款 | exit `1`, path and step limit differences |
| Full unit suite / 完整单测 | all tests pass |
| CI workflow / CI 工作流 | normal case passes and all four defects fail closed |

## Local commands / 本地命令

```bash
python -m pip install -e .
python examples/refund_business_case.py \
  --behavior normal \
  --out work/refund-business-case/candidate.trace.json
agent-regression compare \
  --config examples/refund-business-case/compare.config.json
python -m unittest discover -s tests -v
```

## Boundary / 边界

The case proves deterministic contract enforcement and Trace evidence. It does
not prove that a model will always produce the correct claims, that a live
payment system is safe, or that every framework lifecycle is captured. A real
integration must expose trustworthy claims, use isolated tools, and add its own
domain cases.

该案例证明的是确定性契约检查和 Trace 证据链。它不证明模型永远会输出正确 claims，
也不证明真实支付系统安全，更不代表所有框架生命周期都已被采集。真实接入仍需要
暴露可信 claims、使用隔离工具并补充自己的业务用例。
