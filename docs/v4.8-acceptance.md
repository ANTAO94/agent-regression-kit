# v4.8 acceptance / v4.8 验收

v4.8 adds per-tool call-count Contracts. A project can require a tool to run at
least, at most, or exactly a configured number of times, optionally only for
calls with matching arguments. This makes duplicate side effects, accidental
loops and cost-expanding retries visible in the same deterministic report as
other Agent regressions.

v4.8 增加按工具维度的调用次数契约。项目可以要求某工具至少、最多或恰好执行指定次数，
还可以只统计参数匹配的调用。这样，重复副作用、意外循环和成本膨胀的重试就能和其他
Agent 回归一样进入确定性的报告和 CI 门禁。

## Acceptance matrix / 验收矩阵

| Check / 检查 | Expected result / 预期结果 |
| --- | --- |
| Existing Contract without `tool_limits` / 旧 Contract 未配置 | unchanged behavior; no migration / 行为不变，不需要迁移 |
| `min_calls` / 最小次数 | candidate fails when matching calls are missing / 匹配调用不足时失败 |
| `max_calls` / 最大次数 | candidate fails when matching calls repeat / 重复调用超过上限时失败 |
| Exact count / 恰好次数 | set both `min_calls` and `max_calls` to the same value / 两个值设为相同数字 |
| Argument-scoped limit / 参数范围 | only calls matching `arguments` are counted / 只统计参数匹配的调用 |
| Diagnostic / 诊断 | exit `1`, `tool_count` includes rule, path and observed count / 退出 `1`，报告规则、路径和实际次数 |
| Invalid rule / 非法规则 | exit `2` with a clear validation error / 退出 `2` 并明确指出配置错误 |
| Refund case / 退款案例 | duplicate refund is blocked by `tool_count`, path and step limit / 重复退款被次数、路径和步骤上限共同阻断 |
| Full suite and release / 完整套件与发布 | all tests, clean install and release checks pass / 测试、干净安装和发布检查全部通过 |

## Configuration / 配置

```json
{
  "contract": {
    "tool_limits": [
      {"tool": "get_order", "min_calls": 1, "max_calls": 1},
      {"tool": "refund_order", "min_calls": 1, "max_calls": 1},
      {
        "tool": "get_shipping",
        "arguments": {"order_id": "123"},
        "max_calls": 1
      }
    ]
  }
}
```

`tool` is required. Set only `min_calls` for a lower bound, only `max_calls`
for an upper bound, or both for an exact range. Bounds are non-negative
integers and `min_calls` cannot exceed `max_calls`. The optional `arguments`
object uses the same exact argument matching as `must_call`; the count only
includes calls that match both the tool and the arguments.

`tool` 是必填项。只设置 `min_calls` 表示下限，只设置 `max_calls` 表示上限，同时设置
两个值表示范围或恰好次数。边界必须是非负整数，且 `min_calls` 不能大于 `max_calls`。
可选的 `arguments` 对象和 `must_call` 使用相同的精确参数匹配逻辑；只有工具名和参数
都匹配的调用才会计数。

## Diagnostics / 诊断

When a limit fails, the report contains a `tool_count` difference:

```json
{
  "category": "tool_count",
  "path": "tool_calls.count.refund_order",
  "baseline": {"tool": "refund_order", "min_calls": 1, "max_calls": 1},
  "candidate": 2,
  "message": "tool call count for 'refund_order' must be between 1 and 1; observed 2"
}
```

`baseline` here means the configured Contract rule, not a claim that the
reviewed Trace itself contained a particular number. This distinction keeps
the report useful when a rule is stricter than the original baseline.

失败时报告会生成 `tool_count` 差异。这里的 `baseline` 表示配置中的契约规则，不表示
审核 Trace 必然包含某个次数；即使新规则比旧 baseline 更严格，报告语义仍然清晰。

```bash
python -m pip install -e .
python examples/refund_business_case.py \
  --behavior normal \
  --out work/refund-business-case/candidate.trace.json
agent-regression compare \
  --config examples/refund-business-case/compare.config.json

PYTHONPATH=src python3 -m unittest discover -s tests -q
```

The duplicate-refund case intentionally fails and should include
`tool_count`, `behavior_path` and `step_limit` among its diagnostics.

重复退款案例故意失败，报告中应至少包含 `tool_count`、`behavior_path` 和 `step_limit`。

## Safety boundary / 安全边界

Call counts are evidence constraints, not authorization. Keep `must_not_call`
for dangerous tools, use `path_rules.extra_calls` to control tolerant paths,
and use `side_effects` or an external transaction boundary to verify actual
state changes. A count rule cannot prove that a tool returned the right data or
that an Agent interpreted it correctly.

调用次数是证据约束，不是权限控制。危险工具仍要使用 `must_not_call`，放宽路径仍要用
`path_rules.extra_calls` 控制，真实状态变化还要用 `side_effects` 或外部事务边界验证。
次数规则不能证明工具返回了正确数据，也不能证明 Agent 正确解读了结果。
