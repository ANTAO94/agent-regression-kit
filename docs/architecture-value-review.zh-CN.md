# 架构与开源价值复审

日期：2026-09-22。范围：当前代码、HelpPilot 接入、项目初始化和回归证据。

## 判断

具有开源意义，适合定位为“可嵌入评测平台和 CI 的 Agent 行为契约测试库”。当前适合工程试点，尚没有足够证据
称为广泛验证的成熟框架。发布次数、用例数和 CI 绿色不能替代真实用户价值验证。

## 架构责任与收益

| 部分 | 当前责任 | 评测工程价值 | 主要约束 |
| --- | --- | --- | --- |
| Recorder / Adapter | 将实际行为转换成 Trace | 跨运行时统一证据、关联调用和结果 | 完整性依赖采集边界 |
| Trace 校验 | 检查结构、序号和调用关联 | 提前发现无效输入 | 有效结构不证明真实或完整 |
| Compare / Contract | 差异、断言、次数、路径、跨步骤关系和状态 | 给出确定性、可解释的业务失败 | 规则由业务方制定并审核 |
| Report / CLI / CI | 输出差异并决定流水线是否通过 | 将测试结果接入日常交付 | 配置和安装示例也需要实际验收 |
| Study / Benchmark / Readiness | 组织证据、采样和审计 | 支持可复现分析 | 文件一致不代表样本代表性或来源真实性 |

框架的良好基础是：采集与判定分离，公共数据格式明确，核心无需模型供应商依赖，报告能定位具体字段，
已有路径容忍、额外调用约束和状态契约。这些能承载比纯接口响应比较更丰富的测试。

复杂度集中在 contracts.py（本次检查约 1658 行）和 cli.py（约 1272 行）。行数不是缺陷证据，但结合这些模块
同时承担配置校验、路径匹配、状态规则和命令调度，未来修改容易交叉影响。优先按断言、调用策略、路径和状态拆分内部实现，
保持已有公共 API；无需立即拆成多个发布包。

## 本轮暴露的评测方法问题

HelpPilot 原有 claims 读取 mutation 标签，导致实际回答错误也可能通过。这个问题等于评测接入层替被测对象填写答案。
修复将输出解析与期望规则分开，并在 mutation=none 时改变实际回复验证门禁。

只采集预期动作会使未知行为消失；原有工具白名单因此看不到额外 CRM 写操作。修复保留所有日志动作。
但未记录的副作用仍需执行边界拦截或前后状态快照，框架无法仅凭 Trace 推断。

检索 ID 不是检索证据本身；修复记录实际返回正文，并验证 ID 不变但正文损坏会失败。
这证明正文差异被捕获，不等于证明自然语言回答被正文支持。固定 reviewer 的 grounded=true 不作为模型事实性指标。

人工审批先后关系目前由运行脚本检查。平铺 Trace 中没有独立的审批事件，因此离线比较不能验证整个审批时序。
上游 issue_refund 是模拟日志动作，不能把它称为真实支付副作用验证。

## 开源价值如何成立

价值成立的使用场景是：团队维护一个有工具依赖和业务风险的 Agent，需要在修改 Prompt、工具或编排后，
快速回答“哪条业务规则被破坏、对应什么运行证据”。公开 Trace、Contract 和报告格式使团队可以在自己的 CI 中运行，
并由已有评测平台调用；采集器示例、反例和规则审查也能由社区复用。

不能把“已有评测平台无法实现这些能力”作为定位依据。平台完全可以包含轨迹评测、工具断言和回归门禁。
本项目的竞争力需要通过接入成本、诊断质量和可移植性证明，而不是依靠概念独占。

本次没有进行竞品功能或市场份额调研，不据此声称独有能力或市场空白。

## 下一步验收顺序

1. 证据正确性：每个适配器验证实际输出改变会改变 claims、额外动作不会消失、工具正文完整、缺失证据拒绝通过。
2. 可安装性：在新目录运行 init，真实解析生成的版本引用，执行通过与失败路径。字符串断言不足以证明 CI 可用。
3. 业务覆盖：同一项目增加审批拒绝、订单不存在、工具失败、重复退款、合法措辞和合法只读查询；按业务结果审核各自 Contract。
4. 实际价值：收集历史缺陷或真实修改引入的回归。记录预期失败数、误报数、漏报数和读懂报告耗时，区分注入缺陷与历史缺陷。
5. 外部试点：由未参与实现的人完成接入，至少覆盖两个真实修改周期，再决定 API 稳定范围和后续投资。

达成前三项可提高工程可信度；后两项才回答“别人是否愿意持续使用”。当前最值得投资的是可信采集和接入体验，
新增后台、更多审计命令或扩大 benchmark 数量都应由实际使用问题驱动。
