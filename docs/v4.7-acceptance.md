# v4.7 acceptance / v4.7 验收

v4.7 keeps the tolerant path modes from v4.6 useful without leaving them
open-ended. A project may now declare which unmatched extra tool calls are
allowed. Unknown extra calls fail closed and receive a separate diagnostic.

v4.7 延续 v4.6 的放宽路径能力，但不让它变成无边界放行。项目现在可以显式声明
哪些未匹配的额外工具调用是允许的；未知额外调用会 fail-closed，并单独生成可定位
的诊断差异。

## Acceptance matrix / 验收矩阵

| Check / 检查 | Expected result / 预期结果 |
| --- | --- |
| Existing tolerant Contract without `extra_calls` / 旧 Contract 未配置 `extra_calls` | keeps v4.6 compatibility: unmatched extra calls remain allowed / 保持 v4.6 兼容行为：未匹配额外调用仍允许 |
| `extra_calls` allowlist / 额外调用白名单 | only listed tool/argument/result/error rules are accepted / 只有列出的工具、参数、结果和错误状态规则可通过 |
| `extra_calls: []` | no unmatched extra call is accepted / 不允许任何未匹配额外调用 |
| Unknown extra call / 未知额外调用 | exit `1`, `behavior_path` and `extra_tool_call` differences / 退出 `1`，报告路径失败和具体额外调用 |
| Exact mode with `extra_calls` / exact 模式配置白名单 | configuration validation exits `2` / 配置校验退出 `2`，避免含义冲突 |
| Invalid nested rule / 嵌套规则拼写错误 | configuration validation exits `2` with the field name / 退出 `2` 并指出错误字段 |
| Existing exact path / 旧严格路径 | still blocks any extra call / 仍阻断额外调用 |
| Full unit suite / 完整单测 | all tests pass / 全部通过 |
| Dedicated path CI / 路径专用 CI | allowlisted positive case passes; reordered and forbidden cases fail / 白名单正例通过，乱序和危险调用反例失败 |

## Configuration / 配置

```json
{
  "contract": {
    "path_rules": {
      "mode": "ordered_subsequence",
      "any_of": [["get_order", "get_payment_status"]],
      "extra_calls": [
        {"tool": "get_shipping", "is_error": false}
      ]
    },
    "must_not_call": ["delete_order"],
    "max_steps": 3
  }
}
```

`extra_calls` is optional and is meaningful only with
`ordered_subsequence` or `unordered_subset`. A string checks the tool name;
an object can additionally constrain `arguments`, `result` and `is_error`.
When the field is omitted, v4.6 behavior is preserved. When it is present,
every observed call that is not consumed by a required path rule must match at
least one allowlist rule. An empty list is therefore an explicit deny-all
allowlist.

`extra_calls` 是可选配置，只能和 `ordered_subsequence` 或 `unordered_subset` 一起使用。
字符串只检查工具名；对象还可以约束 `arguments`、`result` 和 `is_error`。省略该字段
会保持 v4.6 行为；一旦配置，所有没有被必需路径规则消费的 observed call 都必须匹配
至少一条白名单规则。因此空数组就是“拒绝所有额外调用”的明确配置。

## Diagnostics / 诊断

An unknown extra call produces an `extra_tool_call` difference such as:

```json
{
  "category": "extra_tool_call",
  "path": "tool_calls[1]",
  "baseline": [{"tool": "get_shipping", "is_error": false}],
  "candidate": {"tool": "delete_order", "arguments": {"order_id": "123"}},
  "message": "extra tool call is not allowed by path_rules.extra_calls"
}
```

报告中的 `extra_tool_call` 会告诉使用者：哪一个调用没有被核心业务路径消费、
当前白名单允许什么、候选实际调用了什么。它和 `behavior_path` 同时出现：前者是
局部原因，后者是整体路径契约失败。

## Safety boundary / 安全边界

An allowlist does not replace authorization. Keep `must_not_call` for
dangerous operations, `max_steps` for runaway loops, and assertions, relations,
side effects and structured claims for business invariants. Path matching is
deterministic, reads the candidate Trace and does not execute user code or call
an LLM judge.

白名单不等于权限控制。危险操作仍要配置 `must_not_call`，循环或异常膨胀仍要设置
`max_steps`，业务不变量仍应由 assertions、relations、side_effects 和结构化 claims
表达。路径匹配是确定性的，只读取 candidate Trace，不执行用户代码，也不调用 LLM Judge。
