## 1. 定位与成功标准

目标用户是已经维护 Agent、需要安全修改 Prompt、模型或工具的开发者。产品承诺是：以少量接入代码记录真实行为，用项目自己的业务契约识别有害变化，在 PR 中解释并阻断回归。

用户主流程固定为：接入 → 录制 → 审核基线 → 修改 Agent → 比较 → 理解失败 → 修复或人工更新基线。

Agent 特有价值集中在跨步骤参数依赖、合法路径变化、最终状态、副作用与业务结论。工具不自动知道业务答案；claims 必须来自实际输出，契约由业务方审核。

上一轮按代码变化量分析投入方向只能作为辅助信号：比较逻辑也位于 contracts.py 等模块，compare.py 的修改行数不能单独衡量产品进展。星数、测试数量和版本数量同样不作为产品成熟度分数。

本轮成功需要同时出现：外部维护者能接入、失败报告能解释、真实修改中能发现问题、团队愿意持续保留门禁。以下时间和数量是本项目的试点目标，并非行业标准或通用可靠性保证。

## 2. 产品边界

| 层次 | 责任 | 后续处理 |
| --- | --- | --- |
| 核心 | Trace、录制/受控重放、Contract、比较、脱敏、报告、CI | 优先修复影响日常回归的缺口 |
| 集成 | 框架结果转换、回调、工具边界、状态快照 | 先深入一个真实项目，再按需求扩展 |
| 验证与审计 | benchmark、τ²、AgentDojo、study、readiness | 保持兼容并修复缺陷，放入高级文档 |

先调整文档入口和维护优先级。物理拆包、移动模块和删除顶层导出另行评估；现有导入、命令和退出码保持兼容。只有确认依赖或维护成本构成障碍，才新增命名空间并提供弃用迁移期。

readiness 的 final-v4 是既有工程验收策略。不能把它包装成适用于所有业务的成熟认证；通过摘要校验只说明文件匹配。外部用户研究和未见任务验证继续保留真实状态。新方案调整工作优先级，不追认旧方案的未完成项为通过。

## 4. P0：收敛入口和修正文档

交付物：

- README 主线依次为价值、安装、通过/失败示例、真实接入、规则与 CI；benchmark/study/readiness 进入高级入口。
- 给用户一张任务索引：录制、比较、查看、审核基线；现有高级命令仍可使用。
- 统一解释 `replay` 的记录查看与 `replay_agent_run` 的受控执行；明确回放工具结果不保证在线模型输出确定。
- 修正 README 与手册对 init 生成文件和示例 baseline 的矛盾；模板 baseline 仅对模板场景有效。
- 修正框架接入示例中硬编码 claims 的写法：从实际输出提取，并用“输出错误、工具结果正确”的反例验证。
- 增加一页故障排查：安装失败、配置错误、Agent 执行错误、回归失败分别如何处理。

验收：全新环境照文档完成通过和失败示例；安装后文档链接有效；示例退出码 0/1/2 含义一致。文档预演目标为 15 分钟，维护者执行只算预演，外部人员结果在 P3 单独记录。

## 5. P1：接入一个既有真实项目

先选一个已有独立业务用途、具有至少两个依赖工具步骤的 Agent。优先使用其现有框架；缺少项目时可预选一个 LangGraph 项目用于技术预演。公开项目技术接入不能等同于其维护者采用。

接入交付：

1. 发布包安装与一个明确的运行入口。记录输入、模型/Prompt/工具版本、参数、结果、实际最终输出；不强迫用户填写审计 descriptor。
2. 复用已有转换器或回调，补齐该项目实际遇到的生命周期缺口。记录接入代码量、修改位置和耗时，避免要求修改业务决策逻辑。
3. 形成 10–20 个经过业务审核的案例，涵盖正常、错误资源、漏步骤、结果误读和允许的路径变化；案例数量只是覆盖目标。
4. 模型与工具环境分别说明：固定模型/工具用于确定性 CI；使用真实模型时保留重复运行记录；真实写操作使用隔离资源。
5. 让报告指向失败案例、规则、实际值、期望值和相关调用；接入现有 CI artifact/summary。

验收：发布 wheel 在独立 checkout 可运行；正常案例通过；三类必要错误均失败；至少两种声明允许的变化通过；录制缺失或业务断言取不到字段不能静默通过。若项目支持受控工具替换，再验证旧工具结果驱动新 Agent 代码；不能替换时如实记录限制。

注入错误证明检测机制可用。另收集历史缺陷或真实修改造成的回归，区分两类证据，不用注入错误代替真实价值验证。

## 6. P2：根据失败样本改善规则和排障

进入条件是 P1 已记录实际误报或看不懂的失败报告。优先处理：动态字段、无害额外查询、允许的工具顺序变化、重复调用、最终状态相同但存在多余副作用。

每条改动必须成对验收：一个合法变化通过，一个邻近危险变化阻断。例如忽略 request_id 后，错误 order_id 仍然失败；允许额外只读查询后，额外退款仍然失败。

候选交付包括业务规则示例、配置诊断、按案例聚合的报告、相关调用链定位和基线审核说明。先复用现有规则与 Viewer；只有实际任务无法完成才新增语义、命令或交互。

验收记录包含首次判断失败原因耗时、误报原始计数、漏报原始计数、未支持案例及处理方案。小样本不声明通用准确率。严重错误误放阻断发布；任何规则放宽都保留负向回归用例。

## 7. P3：外部试点与持续使用

目标是 3 名未参与框架实现的使用者，在 3 个具有独立用途的 Agent 项目上试用。维护者自建 pilot 继续承担包兼容性验证，单独列出。

每位参与者按同一任务卡操作：安装、跑示例、接入自己的 Agent、审查 baseline、制造已知错误、读懂报告、接入 CI。首次计时阶段允许查文档；维护者帮助的时间和内容必须记录，帮助后的完成不计为独立完成。

试点目标：至少 2/3 能在 30 分钟内完成示例，至少 2/3 在 90 分钟内完成自定义接入和 CI；至少两个项目连续使用两周或覆盖两个真实业务改动周期。记录安装/下载与接入操作的分别耗时，避免环境差异混淆结论。

交付一份匿名反馈汇总：项目用途、框架与版本、任务完成情况、卡点、帮助次数、修复前后差异、是否保留门禁。至少积累两条经项目负责人确认的真实或历史回归发现记录；若没有发现，则该项继续未验证。

没有参与者时，可以继续做文档预演和公开项目接入，但本阶段保持待执行。招募可准备邀请文本与候选清单；对外联系、公开参与记录和新增模型付费运行需具备相应授权。

## 8. P4：发布验收与停止条件

只有满足以下条件才称为“经过真实试点验证”：

- P1 的核心正负案例与 P2 的合法变化/危险变化配对验证通过。
- 外部试点记录达到 P3 目标；失败样本、人工帮助与未支持项完整保留。
- 至少两个项目保留门禁并覆盖约定使用周期，实际回归价值有负责人确认。
- 受影响测试、旧配置/API 兼容性、构建和干净环境安装通过；涉及集成时运行对应框架 CI。
- 双语主入口与接入指南一致；发布说明区分已验证能力和限制。

若试用者持续无法完成接入，返回 P1；若多数失败是无害差异，返回 P2；若用户接入成功却不愿保留门禁，暂停新增功能并复核使用场景。缺少外部证据时继续维护当前版，不能用新增审计命令替代缺失证据。

建议首次整理与一个项目预演各预留 2–3 个工作日，规则修复按试点问题估算，外部使用至少两个周期。时间是预算参考，不是自动发布期限。

## 9. 本轮暂缓与后续准入

暂缓新 benchmark 矩阵、额外来源绑定、更多成熟度评分、管理后台、多租户、通用 LLM Judge 和同时扩展多语言 SDK。已有能力继续修复缺陷。

新增功能必须回答：哪位用户在什么任务上失败、现有能力为什么不足、如何衡量改善、增加多少接入/维护成本。安全或数据正确性缺陷可直接优先修复，不必等待多个用户反馈。

Java/TypeScript SDK 在出现对应项目接入需求后选一个实施；服务端控制台在多个团队明确需要共享报告和协作审核后另立方案；物理拆包在依赖与维护成本有证据后实施，并保留兼容导入。
