1. 它到底解决什么问题？#

AI Agent 的回归测试和传统接口流量回放有相似之处，但观察对象更丰富：一次 Agent 运行不只是“请求进、响应出”，中间还包含模型决策、工具选择、参数、工具结果、再次思考、最终结构化结论，以及可能产生的业务副作用。

Traditional API replay

传统接口回放关注什么

通常保存请求和响应，重新发送请求，然后断言 HTTP 状态码、响应字段、延迟或错误码。它假设接口边界相对稳定，响应的主要语义在一个 JSON 中。

典型问题：“这个接口在新版本里是否返回了不兼容的字段？”

Agent regression

Agent 回归还要关注什么

除了最终答案，还要检查 Agent 有没有调用正确工具、参数是否正确、工具结果有没有被误读、是否绕过权限、是否多走了危险路径、是否在多轮之间污染状态。

典型问题：“我改了 Prompt 或模型后，它还会按允许的方式完成这件事吗？”

◎
一句话判断项目价值如果只比较最后一句文本，它很像普通文本测试；如果比较整个可观察行为链，它就是 Agent 的“单元测试 + 契约测试 + CI 回归门禁”基础层。

修改 Prompt

发现工具选择或参数悄悄变化，而不是只看回答“好像还行”。

更换模型

允许明确声明哪些文字可以变化，同时继续校验 claims、工具和结果。

增加工具

限制危险工具、最大步骤数和允许的完整工具路径，避免 Agent 绕远路。

2. 先把关键名词说清楚#

第一次接触 Agent 评测时，很多困难不是代码，而是名词混在一起。下面的定义以本项目的实际边界为准。

名词英文含义在项目里具体指什么
Agent智能体接收用户请求、决定调用哪些工具、根据结果继续执行并给出答案的程序。可以是 LangChain、Spring AI、OpenAI SDK 或自研代码。
Tool工具Agent 可以调用的外部能力，例如查询订单、查数据库、搜索、发起支付或调用 MCP Server。
Adapter适配器把某个框架的 Agent 调用方式翻译成 Kit 能观察的两个动作：context.call_tool() 和 context.final_answer()。
ToolExecutor工具执行器真正执行工具调用并返回结果的边界。可以是内存 Fixture、自定义执行器或 MCP 客户端。
Trace运行轨迹一次 Agent 运行的 JSON 证据，包含工具调用、工具结果、最终答案、结构化 claims 和元数据。
baseline基线经过人工审核、被认为正确的行为证据。它是“期望行为”，不是每次 CI 自动覆盖的临时结果。
candidate候选版本当前代码、Prompt 或模型生成的新 Trace。比较器会判断它相对 baseline 发生了什么变化。
Replay回放读取已有 Trace 并验证其结构；它不是重新调用真实模型，也不是自动重放所有线上副作用。
Regression回归一次改动导致原来正确的可观察行为被破坏，例如工具参数错误、结果误读或非法路径。
Assertion断言对候选 Trace 中某个字段提出明确要求，例如 order_status == "paid"。
Contract契约比“和 baseline 是否相同”更主动的行为规则，例如必须调用某工具、禁止调用某工具、允许多条合法路径。
Normalizer归一化器在比较前把确定的动态值转换成稳定形式，例如把时间戳归一化为 <timestamp>。
Redaction脱敏在 Trace 写入前遮蔽常见敏感字段或显式传入的 secret，降低 API Key、Token 进入报告的风险。
Claims结构化结论Agent 对最终结果的机器可比较表达，例如 {"order_status": "not_shipped"}；比从自然语言中猜事实可靠。
Scenario场景一个可重复的输入和工具世界，例如“查询订单 123”，通常包含 Scenario JSON 或工厂函数。
World State业务世界状态订单、库存、权限等会被 Agent 改变的状态。可以在运行前后做快照来检查副作用。
MCPModel Context Protocol一种让 Agent 发现和调用工具、资源、Prompt 等能力的协议。本项目可通过 stdio 或 Streamable HTTP 接入。
SSEServer-Sent Events服务器向客户端持续推送事件的 HTTP 流格式。它适合记录长连接通知和流式响应。
CIContinuous Integration持续集成系统，例如 GitHub Actions。每次 Pull Request 自动运行测试并在失败时阻止合并。
LLM Judge大模型裁判让另一个模型评价回答“像不像正确答案”。本项目的核心比较器不是 LLM Judge，而是确定性结构比较。

3. 一次运行如何变成回归证据#

把系统想成一条证据流水线：Agent 负责产生动作，Recorder 负责记录，Trace 负责保存，Compare 负责解释差异，CI 负责决定是否阻断。

flowchart LR
  Input[用户请求或场景] --> Agent[Agent / Framework]
  Agent --> Adapter[Adapter 适配边界]
  Adapter --> Recorder[Recorder 录制器]
  Recorder --> Executor[ToolExecutor 工具执行器]
  Executor --> Tools[Fixture / MCP / 自定义工具]
  Recorder --> Trace[脱敏 AgentTrace]
  Baseline[审核后的 baseline] --> Compare[结构化比较]
  Trace --> Candidate[candidate Trace]
  Candidate --> Compare
  Compare --> Report[JSON / Markdown / JUnit]
  Report --> Gate[CI 退出码]
  Gate -->|通过| Pass[允许继续]
  Gate -->|回归| Fail[阻断并审核]

图意：Agent 只需要把可观察行为接到统一边界；之后的录制、比较、报告和 CI 门禁可以复用。

输入

用户请求、Scenario JSON 或多轮请求。输入应稳定、可复现，并明确使用什么工具世界。

证据

工具调用和结果成对出现，最终答案必须是 Trace 最后一个事件，claims 可选但强烈建议提供。

决策

比较器返回差异列表和 passed；CLI 再把它转换成 0、1 或 2 的退出码。

4. 五分钟跑通完整闭环#

下面使用仓库自带的确定性订单场景，不需要 API Key、真实模型、网络或外部数据库。先验证工具本身，再接入你的 Agent。

1安装与确认版本

python3 -m venv .venv
.venv/bin/pip install -e .
.venv/bin/agent-regression --version

开发仓库使用 -e .（editable install，可编辑安装），代码修改后无需反复打包。使用发布版本时可以从 GitHub 安装并固定 tag，例如 git+https://github.com/ANTAO94/agent-regression-kit.git@v4.32.0。

2先录一份经过确认的 baseline

mkdir -p work baselines outputs
.venv/bin/agent-regression record \
  --scenario examples/order-123/baseline.scenario.json \
  --out work/order-123.baseline.trace.json

# 确认内容符合预期后，显式接受为 baseline
.venv/bin/agent-regression baseline accept \
  --trace work/order-123.baseline.trace.json \
  --out baselines/order-123.trace.json

这里的 baseline accept 会先校验 Trace，再把它保存到期望路径。它强调“审核后接受”，避免 CI 每次运行都无意覆盖基线。

3生成一个 candidate 并比较

.venv/bin/agent-regression record \
  --scenario examples/order-123/candidate-ok.scenario.json \
  --out work/order-123.candidate.trace.json

.venv/bin/agent-regression compare \
  --baseline baselines/order-123.trace.json \
  --candidate work/order-123.candidate.trace.json \
  --format markdown \
  --out outputs/order-123.diff.md

如果换成 candidate-regression.scenario.json，会产生一个故意错误的工具参数，比较结果会出现 tool_arguments 差异，并返回退出码 1。

4验证 Trace 和查看回放摘要

.venv/bin/agent-regression validate \
  --trace baselines/order-123.trace.json

.venv/bin/agent-regression replay \
  --trace work/order-123.candidate.trace.json \
  --out outputs/order-123.replay.json
agent-regression-kit/ ├── baselines/ # 人工审核后的期望 Trace ├── work/ # 本次运行的临时 candidate ├── outputs/ # diff、JUnit、Markdown、趋势报告 ├── examples/ # 可重复的场景和本地 Fixture ├── src/agent_regression/ # 核心库与 CLI ├── schema/ # AgentTrace v0.1 JSON Schema └── .github/actions/ # 可复用 GitHub Actions

不要把 work 当成 baselinework/ 是运行产物，baselines/ 是经过审核的产品行为契约。只有确认行为变化是有意的，才更新 baseline。

5. Trace：项目真正比较的是什么#

AgentTrace 是项目的证据格式，当前运行时版本是 0.1。它不是模型内部思维链，也不是把隐藏推理暴露出来；它只保存接入边界上明确产生的可观察事件。

sequenceDiagram
  participant A as Agent
  participant R as Recorder
  participant T as ToolExecutor
  participant X as Tool or MCP
  A->>R: call_tool(name, arguments)
  R->>T: execute normalized request
  T->>X: perform tool call
  X-->>T: result or error
  T-->>R: ToolExecutionResult
  R-->>A: return result
  A->>R: final_answer(text, claims)
  R->>R: redact and validate
  R-->>R: write AgentTrace JSON

图意：Recorder 只记录接入边界上的调用和结果；它不负责决定 Agent 使用哪个框架，也不负责替模型生成 claims。

6. baseline 与检查规则#

这是最重要、也最容易误解的一节。项目里有两类规则：一类决定 baseline 差异是否阻断；另一类定义候选 Trace 必须满足的行为契约。两者作用不同，不能混用。

allow_categories / allow_paths

作用是放宽 baseline 比较的阻断条件。例如最终文本允许变化，或者某个 request ID 本来就动态。

注意：差异不会消失，仍会写进报告；只是这一项不再让比较失败。

contract

作用是约束 candidate 必须怎样运行。例如必须调用 get_order、禁止调用 delete_order、最多 5 步或必须产生某种副作用。

契约失败会产生明确的 contract_assertion、required_tool 等差异。

6.1 配置 baseline 检查项、断言和噪音过滤#

你可以把比较配置写成项目文件，避免每次命令行重复传参。下面是一份覆盖主要能力的例子：

{
  "baseline": "baselines/order-123.trace.json",
  "candidate": "work/order-123.candidate.trace.json",
  "format": "markdown",
  "report": "outputs/order-123.diff.md",
  "allow_categories": ["final_answer"],
  "allow_paths": ["tool_calls[0].arguments.request_id"],
  "final_answer_mode": "claims-only",
  "secret_values": ["local-test-secret"],
  "contract": {
    "must_call": [
      {"tool": "get_order", "arguments": {"order_id": "123"}}
    ],
    "must_not_call": ["delete_order"],
    "assertions": [
      {"path": "final_answer.claims.order_status", "equals": "not_shipped"},
      {"path": "final_answer.claims.order_id", "exists": true}
    ],
    "ignore_paths": ["tool_results[*].result.request_id"],
    "normalizers": [
      {"path": "tool_results[*].result.created_at", "type": "timestamp"},
      {"path": "tool_results[*].result.items", "type": "sort"}
    ],
    "max_steps": 5,
    "tool_limits": [
      {"tool": "get_order", "min_calls": 1, "max_calls": 1}
    ],
    "tool_allowlist": [
      "get_order",
      {"tool": "get_shipping", "arguments": {"order_id": "123"}}
    ],
    "argument_rules": [
      {
        "tool": "get_order",
        "path": "tenant_id",
        "operator": "equals_path",
        "right_path": "metadata.input.tenant_id",
        "message": "不得跨租户查询"
      },
      {
        "tool": "refund_order",
        "path": "amount",
        "operator": "less_or_equal_path",
        "right_path": "tool_results[0].result.paid_amount",
        "message": "退款金额不得超过实付金额"
      },
      {"tool": "refund_order", "path": "admin_override", "operator": "absent"}
    ],
    "path_rules": {
      "mode": "ordered_subsequence",
      "any_of": [[
        {"tool": "get_order", "arguments": {"order_id": "123"}}
      ]],
      "extra_calls": [
        {"tool": "get_shipping", "is_error": false}

      {"path": "orders.123.status", "from": "paid", "to": "cancelled"}

path_rules.mode选择严格、允许额外调用但保持顺序、允许额外调用且可乱序三种模式exact / ordered_subsequence / unordered_subset失败时是

tool_allowlist定义当前场景允许调用的完整工具目录，可按参数精确匹配get_order、refund_order未命中生成 unauthorized_tool_call

state_equivalence把已声明的替代动作归为同一意图，并比较最终状态outcome、paths、幂等重复失败生成 state_equivalence 或路径差异

max_steps防止 Agent 无限调用工具5失败时是

6.3 和传统接口回放的断言怎么对应？#

传统接口回放Agent Regression Kit 对应方式建议
响应 JSON 字段等于contract.assertions 或 baseline 的结构比较关键业务结论优先放 claims，再用断言固定。
忽略时间戳、request ID结果字段用 contract.ignore_paths；路径参数用 path_rules.ignore_argument_paths只过滤已知噪音，不要为了“让测试通过”忽略整段结果或业务参数。
请求参数断言工具调用 baseline 比较、must_call.arguments权限、租户、订单号等关键参数不要放宽。
允许多个合法响应path_rules.any_of 或 claims-only把合法范围写出来，不要依赖宽泛的字符串匹配。
接口副作用回滚SnapshotBackend、StateIsolation、side_effects测试环境能 snapshot/restore 才能证明没有污染后续用例。
!
目前不是任意 JSONPath / 正则 / 语义判分平台内核只提供确定的路径、时间戳归一化、列表排序、字段断言和结构化比较。复杂业务语义应在 Adapter 或 claims 中明确表达；不要假设工具包会从一句自然语言自动推断“事实”。

6.4 状态等价契约：降低误报但不放宽安全边界#

严格路径适合“每一步都必须一样”的场景，但真实业务可能允许换支付方式、失败后重试或重复执行幂等更新。v4.13 用 state_equivalence 表达这些经过审核的等价关系，并用 attempt_policy 要求成功证据、用 state_scope 检查未声明状态：只归并你在 path_rules.any_of 中写出的规则，订单号、租户号、金额和资源参数仍然精确检查。

outcome 模式做什么

按照 state_equivalence.ignore_argument_paths 对已声明规则分组；candidate 必须命中组内某条规则的精确工具名和未忽略参数。路径参数的传输噪音应单独使用 path_rules.ignore_argument_paths，且 baseline 已声明字段不会被忽略。

它不会做什么

不会根据工具名称相似、LLM 判断或“看起来成功”自动推断等价。失败尝试、工具别名、幂等重复默认全部关闭，必须显式配置并添加错误对象/越权资源的负向测试。

"state_equivalence": {
  "mode": "outcome",
  "paths": ["world_state.final.orders.123.status"],
  "ignore_argument_paths": ["payment_method_id"],
  "tool_aliases": [["exchange_delivered_order_items", "modify_pending_order_items"]],
  "allow_failed_expected": true,
  "idempotent_tools": ["modify_pending_order_address"]
}

推荐先阅读状态等价契约说明，再运行正例和负例。完整的 τ²-bench 结果在 v4.13 达到 267 true pass、153 true block、0 false alarm、0 missed failure，但 v4.14 将它明确标为 calibration 证据，不是留出数据泛化成绩。

7. 接入自己的 Agent#

接入的关键不是把整个框架改造成 Kit，而是在 Agent 和工具执行层之间放一层很薄的 Adapter。它只需要把“调用工具”和“给出最终答案”转发到统一上下文。

flowchart LR
  Framework[你的框架 Agent] --> Invoke[invoke / run / execute]
  Invoke --> Adapter[CallableAgentAdapter]
  Adapter --> Context[RunContext]
  Context --> Call[context.call_tool]
  Context --> Answer[context.final_answer]
  Call --> Executor[你的 ToolExecutor 或 MCP]
  Answer --> Trace[AgentTrace]
  Executor --> Trace

图意：框架的内部实现留在项目内，Kit 只要求两个可观察出口，从而保持跨框架。

7.1 最小同步 Agent 示例

import json
from pathlib import Path

from agent_regression import (
    CallableAgentAdapter,
    FixtureTools,
    record_run,
)


def invoke_framework(request, context):
    # 真实项目里，这里可以调用你的 LangChain、Spring AI、OpenAI SDK
    order_id = request["order_id"]
    order = context.call_tool("get_order", {"order_id": order_id})
    context.final_answer(
        f"订单 {order_id} 的状态是 {order['status']}。",
        {"order_id": order_id, "order_status": order["status"]},
    )


adapter = CallableAgentAdapter(
    {"name": "my-order-agent", "version": "1.0.0"},
    invoke_framework,
)
tools = FixtureTools({"get_order": {"status": "not_shipped"}})
trace = record_run(
    adapter,
    {"order_id": "123"},
    tools,
    run_id="my-order-agent-123",
)

Path("work/my-agent.trace.json").parent.mkdir(parents=True, exist_ok=True)
Path("work/my-agent.trace.json").write_text(
    json.dumps(trace.to_dict(), ensure_ascii=False, indent=2) + "\n",
    encoding="utf-8",
)

7.2 适配器必须遵守的两个约定

工具调用

不要让 Agent 直接绕过 Recorder 调用真实工具。所有需要被比较的工具都要通过 context.call_tool(tool, arguments)，这样调用、结果、错误状态才能成对写进 Trace。

最终答案

在每次运行结束时调用一次 context.final_answer(text, claims)。claims 是可选的结构化业务结论，但要做可靠评测时建议提供。

7.3 如果已有自己的 ToolExecutor

不使用 MCP 也可以。只要实现类似下面的最小边界，就能复用同一套录制器：

class MyToolExecutor:
    def call(self, tool: str, arguments: dict):
        if tool == "get_order":
            return order_service.get(arguments["order_id"])
        raise KeyError(tool)

# 录制器负责事件和脱敏；执行器负责真正调用工具
trace = record_run(
    adapter,
    request,
    MyToolExecutor(),
    run_id="production-like-order-123",
)
i
不需要先拥有成熟 Agent可以先使用项目内的 ScriptedAgentAdapter、RuleBasedOrderAgentAdapter 或 Fixture 工具验证 Trace 和 compare，再逐步接入真实框架。工具包测的是接入边界是否正确，不要求一开始就有生产级模型。

8. 异步 Agent 与一次运行内的并行工具#

“多个场景并行录制”和“一个 Agent 在同一轮并行调用多个工具”是两件事。v2.9 处理后者，并把并行形状写进 Trace，防止一次改动把并发逻辑悄悄降级成串行。

sequenceDiagram
  participant A as Async Agent
  participant R as Async Recorder
  participant O as Tool get_order
  participant S as Tool get_shipping
  A->>R: create call-1 and call-2
  par same parallel_group lookup
    R->>O: await get_order
    O-->>R: result for call-1
  and
    R->>S: await get_shipping
    S-->>R: result for call-2
  end
  R->>R: preserve creation order and call IDs
  R-->>A: final answer event last

图意：实际完成时间可以变化，但 Trace 保留调用创建顺序、稳定 call ID 和 parallel group；并发形状变化会被识别为差异。

import asyncio
from agent_regression import AsyncCallableAgentAdapter, record_async_run


async def invoke_async(request, context):
    order, shipping = await asyncio.gather(
        context.call_tool(
            "get_order", {"order_id": request["order_id"]},
            parallel_group="lookup",
        ),
        context.call_tool(
            "get_shipping", {"order_id": request["order_id"]},
            parallel_group="lookup",
        ),
    )
    context.final_answer(
        "查询完成",
        {"order": order, "shipping": shipping},
    )


trace = record_async_run(
    AsyncCallableAgentAdapter(
        {"name": "async-order-agent", "version": "1.0.0"},
        invoke_async,
    ),
    {"order_id": "123"},
    async_tools,
    run_id="async-order-123",
)
顺序概念说明
调用创建顺序决定 call-1、call-2，用于稳定比较。
实际完成顺序可能因网络或工具延迟变化，不应该成为无意义的回归差异。
Trace 事件顺序保持可比较的调用与结果结构，最终答案仍然最后出现。
parallel_group明确声明哪些调用属于同一并行组；组结构变化会产生 execution_concurrency 差异。

9. MCP 接入：从本地 Fixture 到真实 Server#

MCP（Model Context Protocol）让 Agent 用统一协议发现和调用工具、资源、Prompt 等能力。项目提供 stdio 和 Streamable HTTP 两种传输方式；测试优先使用仓库自带的确定性 Fixture，不依赖外部服务。

stdio

Streamable HTTP

通过 HTTP POST 发送请求，服务端可以返回 JSON 或 SSE 流，也可以使用 GET 监听事件。适合独立部署的 MCP Server。

9.3 MCP 交互与错误如何进入 Trace

情况记录方式默认安全行为
工具成功tool_result.is_error = false，保存结构化结果继续 Agent 运行
工具业务错误is_error = true，保存错误状态和内容不把错误伪装成成功
JSON-RPC / 协议错误转换成明确的 MCP 异常或错误结果不自动重试未知副作用

!

10. 状态、副作用与多轮 Session#

如果 Agent 会取消订单、扣库存、修改权限，只比较工具结果还不够。测试必须知道运行前后的世界状态，并在用例结束后把状态恢复，防止前一个测试污染后一个测试。

flowchart LR
  Before[初始 World State] --> Snapshot[snapshot 快照]
  Snapshot --> Run[Agent run]
  Run --> After[最终 World State]
  After --> Effect[side_effects 断言]
  Effect --> Restore[restore 恢复]
  Restore --> Clean[下一个用例从干净状态开始]
  Run --> Error[Agent 异常]
  Error --> Restore

图意：无论正常结束还是异常结束，都应走 restore；side_effects 只检查明确声明的业务状态变化。

10.1 SnapshotBackend 示例

from agent_regression import isolated_record_run


class TestDatabaseState:
    def snapshot(self):
        return read_test_rows_as_json()

    def restore(self, snapshot):
        replace_test_rows_from_json(snapshot)


trace = isolated_record_run(
    my_agent,
    {"order_id": "123", "action": "cancel"},
    my_tools,
    state_backend=TestDatabaseState(),
    run_id="cancel-order-123",
)

SnapshotBackend 只规定两个职责：snapshot() 返回可脱离原对象的测试状态，restore(snapshot) 把它恢复。它可以连接测试数据库、Redis、内存 Fixture 或服务模拟器，但不会自动发现隐藏的外部写入。

10.2 多轮 Session

多轮流程应使用 Session，而不是把所有对话拼成一个不可读的最终字符串。每一轮仍然拥有独立 Trace，Session 比较器按轮次对齐，并可以检查上一轮最终状态是否成为下一轮初始状态。

.venv/bin/agent-regression session-record \
  --scenario examples/order-session/session.scenario.json \
  --out work/order-session.json

.venv/bin/agent-regression session-compare \
  --baseline baselines/order-session.json \
  --candidate work/order-session.json \
  --format markdown \
  --out outputs/order-session.md

11. 稳定性评测：重复运行不是简单回放#

模型采样、网络延迟和工具状态可能让同一个输入偶尔走不同路径。单次 baseline/candidate 比较只能回答“一次是否变化”；稳定性评测会隔离地重复运行同一个场景，并把指标变成门禁。

pass_rate

重复运行中与 baseline 比较通过的比例。

claims_match_rate

结构化业务结论和 baseline 一致的比例。

tool_error_rate

运行中工具错误的比例，适合发现不稳定依赖。

path_variant_count

观察到的完整工具路径数量，用于发现路线漂移。

.venv/bin/agent-regression stability \
  --baseline baselines/order-123.trace.json \
  --scenario examples/order-123/baseline.scenario.json \
  --repeats 10 \
  --workers 4 \
  --min-pass-rate 0.95 \
  --min-claims-match-rate 1.0 \
  --max-tool-error-rate 0.05 \
  --max-path-variants 1 \
  --final-answer-mode claims-only \
  --format markdown \
  --out outputs/stability.md
i
这不是统计学证明重复 10 次只能说明这 10 次的证据。它不能穷尽模型所有路径，也不是 LLM Judge。它的价值是把“偶尔会错”变成 pass rate、claims 一致率、工具错误率和路径变化这些可审核指标。

12. 场景覆盖与业务分支覆盖#

Agent 的覆盖率不等于源码行覆盖率。这里统计的是“场景证据是否走过预期工具路径”和“结构化 claims 是否覆盖预期业务结果”。

flowchart LR
  Scenarios[正常 / 异常 / 权限 / 副作用场景] --> Traces[多份 AgentTrace]
  Traces --> ToolPaths[工具调用路径集合]
  Traces --> Claims[结构化 claims]
  ToolPaths --> ExpectedPaths[expected-path 门禁]
  Claims --> ExpectedBranches[expected-branch 门禁]
  ExpectedPaths --> CoverageReport[覆盖率报告]
  ExpectedBranches --> CoverageReport
  CoverageReport --> CI[CI 退出码]

图意：覆盖率的对象是“已有场景是否提供证据”，不是声明 Agent 内部所有代码和模型分支都被证明。

.venv/bin/agent-regression coverage \
  --trace-dir work/scenarios \
  --expected-path "get_order" \
  --expected-path "get_order -> cancel_order" \
  --expected-path "get_order -> refund" \
  --include-outcomes \
  --branch-path final_answer.claims.order_status \
  --expected-branch paid \
  --expected-branch cancelled \
  --expected-branch not_found \
  --format markdown \
  --out outputs/coverage.md

--include-outcomes 会把工具路径写成 get_order[ok] 或 get_order[error]。如果任意 expected path 或 expected branch 没有被观察到，命令返回 1，可以直接阻断 CI。

批量录制独立场景可以使用：

.venv/bin/agent-regression batch-record \
  --scenario-dir examples/order-123 \
  --out-dir work/scenarios \
  --workers 4 \
  --format markdown \
  --report outputs/batch-record.md

批量录制要求每个 ScenarioCase 创建独立 Agent 和工具执行器；有界线程不会自动修复框架线程安全，也不会自动隔离进程级环境变量。

15.3 CI 中的三种门禁组合

回归门禁

比较 baseline/candidate，检查工具、结果、claims、流程和最终文本。

稳定性门禁

重复运行场景，检查通过率、错误率和路径变体。

覆盖门禁

检查正常、异常、权限和副作用路径是否都已经有证据。

建议的 PR 流程是：先录 candidate → 生成 JSON/Markdown/JUnit → 在 PR 中审核差异 → 如果是意外变化修代码 → 如果是有意变化再单独更新 baseline。

16. 报告格式与退出码#

JSON

机器可读，适合后续聚合、历史趋势和自动化处理。通常包含每个差异的 category、path、baseline、candidate。

Markdown

人最容易读，适合 GitHub Job Summary、PR 评论和本地审核。

JUnit XML

适合 CI 测试结果面板。工具会把阻断差异转换为失败用例。

退出码含义处理方式
0比较、覆盖或稳定性门禁通过允许继续流水线。
1发现阻断性回归、缺失覆盖、稳定性阈值未达标或最新历史点失败查看 Markdown/JSON，决定修代码还是审核更新 baseline。
2输入、Trace、配置或环境无效先修命令、路径、JSON 或运行环境，不要把它当业务回归。

16.1 如何阅读一条差异

{
  "category": "tool_arguments",
  "path": "tool_calls[0].arguments",
  "baseline": {"order_id": "123"},
  "candidate": {"order_id": "132"}
}
  1. 先看 category：它告诉你变化属于工具名、参数、工具结果、答案文本、claims、状态、并发还是契约。
  2. 再看 path：它告诉你 Trace 中的具体位置；tool_calls[0] 表示第一个工具调用。
  3. 最后对照 baseline/candidate：判断这是 Bug、噪音、还是经过评审的产品变化。

17. 技术架构：各组件的职责边界#

设计原则是：接入层负责把框架动作翻译出来，执行层负责工具边界，Trace 负责证据格式，比较层负责确定性差异，报告层负责展示，CI 负责门禁。

flowchart TD
  Adapter[AgentAdapter]
  Adapter --> Context[RunContext / AsyncRunContext]
  Context --> Recorder[record_run / async_record_run]
  Recorder --> Executor[ToolExecutor]
  Executor --> Fixture[FixtureTools]
  Executor --> MCP[MCP Client]
  Recorder --> Model[AgentTrace v0.1]
  Model --> Comparator[compare_traces]
  Comparator --> Contract[ContractPolicy]
  Comparator --> Reports[Report Renderers]
  Reports --> CLI[CLI and GitHub Action]
  CLI --> Exit[Exit code gate]

图意：每一层只有一个主职责，比较策略不应该散落到框架适配器或报告渲染器里。

组件职责明确不负责什么
AgentAdapter将框架 Agent 的工具调用和最终答案接入上下文。不比较、不评分、不管理 CI。
Recorder给事件排序、配对调用与结果、脱敏、校验 Trace。不决定 Agent 应该选哪个工具。
ToolExecutor执行工具并返回正常或错误结果。不负责 baseline 策略。
AgentTrace提供稳定、可持久化的证据模型和 v0.1 校验。不保存隐藏思维链。
ComparisonPolicy决定允许哪些差异、最终答案用 exact 还是 claims-only。不从散文中推断业务事实。
ContractPolicy执行断言、工具约束、噪音过滤、路径和副作用规则。不做任意正则和模型判分。
Reporter把结果渲染成 JSON、Markdown、JUnit。不改变比较结论。
History聚合已有报告并计算趋势。不作为在线数据库或 Dashboard。

17.1 为什么保持 AgentTrace schema v0.1 不轻易变化

产品版本和证据 schema 版本是两条线。v4.0 可以增加兼容检查、迁移入口、历史聚合、SDK 或报告能力，而不必悄悄改变旧 Trace 的解释方式。可选的 world state、session、coverage、stability、async execution metadata 都挂在现有边界上，保证已有证据仍可读取。

17.2 比较器当前采用的简化

  • 工具调用按事件顺序对齐，不做最优序列匹配；顺序变化会被明确报告。
  • 工具结果会检查结构化内容和 is_error，不会把“错误结果”当作“没有结果”。
  • claims 必须由 Adapter 或场景显式产生，比较器不从自然语言反向抽取事实。
  • 并发组由 Adapter 显式声明，工具包不猜测框架内部隐藏的任务。

18. 边界、脱敏和安全注意事项#

Trace 脱敏

  • 默认识别常见敏感字段名称。
  • 自由文本里的 secret 不能自动可靠识别，需要显式传入 --secret-value 或 RedactionPolicy(secret_values=...)。
  • 脱敏降低误泄露风险，但不是完整的数据防泄露系统。

MCP 运行权限

  • stdio MCP Server 以当前用户权限作为本地子进程运行。
  • 只运行你信任的 server command。
  • 生产重试、幂等性和副作用策略必须由真实集成明确决定；Kit 默认不自动重试。

18.1 当前明确不承诺的内容

不承诺原因替代做法
模型质量的统计学证明重复运行只能观察有限样本。用 stability 指标表达当前样本中的稳定性。
从自然语言自动判定事实自由文本有歧义，模型裁判也会引入不确定性。让 Agent 输出 claims，使用确定性断言。

19. 常见问题与排错#

Q1：我必须先有一个真实 Agent 吗？

不需要。先用仓库内的 Scripted/Rule-based Agent 和 Fixture 工具验证回归链路；然后用 CallableAgentAdapter 接入真实 Agent。项目的第一个测试对象是“记录、比较、报告是否正确”，不是模型能力。

Q2：这和接口流量回放到底有什么难点差异？

相似点是保存基线、重放或重跑、比较差异；差异在于 Agent 的行为是路径性的、可能非确定、带工具编排和业务状态。关键测试项从单个响应字段扩展到工具路径、参数、工具错误、结果误读、合法替代路径、状态副作用、并发形状、重复运行稳定性和多轮连续性。

Q3：最终文本经常不同，是否每次都失败？

默认 exact 会比较文本。若业务允许文字变化但要求事实不变，使用 --final-answer-mode claims-only；它只忽略 final_answer.text，不会忽略 claims、工具调用、参数、结果或错误状态。

Q4：baseline 什么时候应该更新？

只有当变化是有意的产品行为变更，并且已经审核了工具、参数、结果、claims 和状态影响时更新。不要在 CI 中自动把每次 candidate 覆盖为 baseline。

Q5：allow_paths 和 contract.ignore_paths 有什么区别？

allow_paths 匹配比较器输出的完整差异路径，只是让该差异不阻断；contract.ignore_paths 在比较前深入清理指定 JSON 字段，并支持 [*]。前者是门禁放宽，后者是输入归一化/噪音清理，语义不同。

Q6：运行返回 2 是不是 Agent 回归？

通常不是。退出码 2 表示命令、配置、路径、Trace 格式或环境无效；退出码 1 才是比较发现回归、覆盖缺失、稳定性阈值未达标或最新历史点失败。

Q7：为什么不直接做一个 Dashboard？

Kit 先解决证据格式和 CI 门禁：Trace 可保存、可审核、可复现，比展示层更基础。v3.1 的 history 是文件型趋势聚合器，未来可以在不改变核心证据的前提下接入 Dashboard。

Q8：官方 MCP Server 怎么验证？

仓库提供可手动触发的 .github/workflows/mcp-compatibility.yml，会启动官方 Everything Server，分别检查 stdio 和 Streamable HTTP。它是兼容性 smoke test，不等于支持所有 MCP Server 的全部可选能力。

v4.25固定输入下重复生成的报告和 Trace 是否真的稳定，不能只靠口头保证。三次决策重复、aggregate/case/Trace SHA-256 稳定性检查和独立 CI artifact；明确不等于在线模型方差研究。

v4.0 升级前先跑两条命令

兼容检查是只读的；迁移会写到明确指定的新文件，不会覆盖 baseline：

agent-regression compatibility \
  --public-api-version 4 \
  --trace baselines/order-123.trace.json \
  --config .agent-regression/config.json \
  --report outputs/compare.json

agent-regression migrate trace \
  --trace baselines/order-123.trace.json \
  --out work/order-123.v4.trace.json \
  --report outputs/order-123.migration.json

v3 公共 API 会显示 status=deprecated 和 migration_required=true；Trace schema 0.1 在 v4 暂未改变，所以普通迁移报告通常是 status=no-op。

推荐的实际采用顺序

  1. 先用 Fixture 跑通 record → baseline accept → compare。
  2. 接入一个真实 Agent，只关注工具调用和 claims，不要同时接十个框架。
  3. 为动态字段加最小范围的噪音过滤，并把危险行为写进 Contract。
  4. 对有副作用的场景加入 snapshot/restore，再扩展多轮、异步和 MCP。
  5. 最后接 stability、coverage、history 和 GitHub Actions，让证据进入团队流程。

22. 接入完成检查清单#

  • 本地能够安装并运行 agent-regression --version。
  • 至少有一份经过人工审核的 baseline，且没有把 candidate 自动覆盖回去。
  • Agent 的所有重要工具调用都经过 context.call_tool。
  • Agent 的最终答案包含可比较的结构化 claims，尤其是业务结论。
  • 已明确哪些差异是必须阻断的，哪些动态字段只是已知噪音。
  • 危险工具、最大步骤、合法路径和关键副作用已经写入 Contract。
  • 有状态场景实现了 snapshot/restore，且异常路径也能恢复。
  • 至少有正常、异常、权限或副作用场景中的一部分覆盖门禁。
  • CI 运行和本地运行使用相同的 baseline、candidate 和比较策略。
  • 报告以 JSON/Markdown/JUnit 至少一种形式保存，失败时能定位到 path。
  • Trace 写入前已确认敏感字段和自由文本 secret 的脱敏边界。
