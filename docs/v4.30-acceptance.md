# v4.30 acceptance / v4.30 验收

## Scope / 范围

v4.30 strengthens the recorded sampling-study boundary introduced in v4.29.
When a study manifest enables `integrity.require_trace_hashes`, the evaluator
binds the reviewed baseline, every recorded run Trace and the normalized
comparison policy to SHA-256 digests before evaluating the study. A changed
file is rejected before it can be treated as evaluation evidence.

v4.30 强化 v4.29 引入的记录式 sampling study 边界。当 manifest 开启
`integrity.require_trace_hashes` 后，框架会在评估前把审核过的 baseline、每次运行的 Trace
以及规范化后的 comparison policy 绑定到 SHA-256 摘要。任何文件被修改后，都会先被拒绝，不能
继续作为评测证据。

The feature is intentionally file-level and provider-neutral. It does not
claim that a hash proves the hidden prompt, model output or sampling design is
correct; it proves that the files evaluated are the files named by the
manifest.

这个能力只解决文件级证据完整性，并且与供应商无关。哈希不能证明隐藏 Prompt、模型输出或采样
设计本身正确；它证明的是“本次评估读取的文件，就是 manifest 声明的文件”。

## Manifest / manifest 格式

The v4.29 shape remains valid. For a stronger v4.30 gate, add an optional
`sha256` to every run and an `integrity` object:

v4.29 的 manifest 结构仍然有效。要启用更严格的 v4.30 门禁，在每个 run 中增加可选的
`sha256`，并增加 `integrity` 对象：

```json
{
  "schema_version": "0.1",
  "study_id": "order-provider-sampling",
  "baseline": "baseline.trace.json",
  "runs": [
    {
      "id": "run-001",
      "trace": "runs/run-001.trace.json",
      "sha256": "<sha256-of-runs/run-001.trace.json>"
    }
  ],
  "comparison_policy": {
    "final_answer_mode": "claims-only",
    "contract": {
      "required_claims": ["final_answer.claims.order_status"],
      "must_call": [{"tool": "get_order"}]
    }
  },
  "integrity": {
    "require_trace_hashes": true,
    "baseline_sha256": "<sha256-of-baseline.trace.json>",
    "comparison_policy_sha256": "<sha256-of-normalized-policy>"
  }
}
```

`comparison_policy_sha256` is the canonical SHA-256 of the runtime policy
shape, not merely the text formatting of the manifest. In Python, construct a
`ComparisonPolicy` and hash its `to_dict()` result:

`comparison_policy_sha256` 是运行时策略结构的规范化 SHA-256，不是 manifest 文本格式的哈希。
Python 接入时应先构造 `ComparisonPolicy`，再对 `to_dict()` 的结果计算哈希：

```python
from agent_regression import ComparisonPolicy, canonical_sha256, sha256_file

policy = ComparisonPolicy()
policy_hash = canonical_sha256(policy.to_dict())
baseline_hash = sha256_file("baseline.trace.json")
```

The evaluator also checks that paths stay inside the manifest directory, each
run ID equals the Trace `run_id`, and no secret-like provenance key is present.
`sha256_file` hashes bytes on disk; it does not include raw Trace contents in
the report.

评估器还会继续校验路径必须位于 manifest 目录内、run ID 必须等于 Trace 的 `run_id`，以及
provenance 中不能出现疑似 Secret 的字段。`sha256_file` 直接对磁盘文件字节计算哈希，不会把
Trace 原文写进报告。

## CLI / 命令

The project-owned example now creates a v4.30 integrity-bound study:

项目自带示例现在会创建启用 v4.30 完整性校验的 study：

```bash
python examples/sampling-study/create_demo_study.py \
  --out-dir work/order-123-study

agent-regression study \
  --manifest work/order-123-study/study.json \
  --format markdown \
  --out work/order-123-study/report.md
```

The JSON report contains an `evidence_integrity` section similar to:

JSON 报告会包含类似下面的 `evidence_integrity` 区域：

```json
{
  "trace_hashes_required": true,
  "trace_hashes_verified": true,
  "baseline_sha256": "...",
  "comparison_policy_sha256": "...",
  "runs": [
    {"id": "run-001", "sha256": "..."}
  ]
}
```

The command returns `0` for a passing study, `1` for a valid but failing
Contract/stability gate, and `2` for invalid or tampered evidence. This keeps
business evaluation failures separate from malformed evidence.

命令返回值约定为：study 通过返回 `0`；manifest 合法但 Contract/stability 门禁失败返回 `1`；
证据不合法或被篡改返回 `2`。这样业务评测失败与证据格式/完整性失败是分开的。

## CI acceptance / CI 验收

The core regression workflow now performs both positive and negative checks:

核心回归工作流现在同时验证正向和负向路径：

1. generate the hashed deterministic study and require its report;
2. copy it to an ephemeral directory and append one newline to a run Trace;
3. verify that `agent-regression study` exits with status `2`.

1. 生成带哈希的确定性 study，并把 study report 作为 required report；
2. 复制到临时目录，在一份 run Trace 末尾追加一个换行；
3. 验证 `agent-regression study` 返回状态 `2`。

The tamper test does not modify checked-in fixtures or the normal CI report
directory. It demonstrates the evidence boundary without relying on an online
provider.

篡改测试不会修改仓库中的 Fixture，也不会污染正常 CI 报告目录；它在不依赖在线供应商的情况
下验证证据边界。

## Backward compatibility / 向后兼容

`integrity` and per-run `sha256` are optional. A v4.29 manifest without them
continues to evaluate, and the report still includes observed evidence hashes
for audit visibility. Set `require_trace_hashes` to `true` only after the
manifest writer can produce all required hashes.

`integrity` 和每个 run 的 `sha256` 都是可选字段。不带这些字段的 v4.29 manifest 仍然可以评估；
报告也会包含观察到的证据哈希，方便审计。只有当 manifest 生成方能够提供所有必需哈希后，才应
把 `require_trace_hashes` 设为 `true`。

## Boundaries / 边界

- A digest proves file identity, not semantic correctness or representativeness.
- The framework still does not execute an online provider or hide provider
  credentials on behalf of the caller.
- The comparison policy digest protects against policy drift inside the study
  bundle; it does not review whether the policy is sufficiently strict.
- Provider/model sampling, account isolation and the correctness of the
  Contract remain integration-owner responsibilities.

- 摘要证明文件身份，不证明语义正确性或样本代表性。
- 框架仍不会替接入方执行在线供应商，也不会替接入方管理供应商凭据。
- comparison policy 摘要可以防止 study bundle 内的策略漂移，但不会替你审核策略是否足够严格。
- provider/model 采样、账号隔离以及 Contract 的正确性，仍由接入方负责。
