# v4.9 acceptance / v4.9 验收

v4.9 adds a scenario-level `contract.tool_allowlist`. It makes the permitted
tool catalog explicit: a candidate may call only a listed tool, optionally with
the listed exact arguments. An unauthorized call is reported as
`unauthorized_tool_call` with its concrete trace position.

v4.9 增加场景级 `contract.tool_allowlist`。它把一个业务场景允许使用的工具集合
写成明确契约：候选运行只能调用清单中的工具，也可以进一步限制工具参数。未授权
调用会生成 `unauthorized_tool_call`，并报告 Trace 中的具体位置。

## Scope / 范围

| Contract shape / 配置形态 | Meaning / 含义 |
| --- | --- |
| field omitted / 省略字段 | No tool-catalog restriction; v4.8 and older configs keep their behavior. / 不限制工具目录，v4.8 及更早配置保持原行为。 |
| `tool_allowlist: null` | Treated like omission when loaded from JSON/YAML. / 从 JSON/YAML 加载时等同于省略。 |
| `tool_allowlist: []` | Deny every tool call. Useful for answer-only scenarios. / 拒绝所有工具调用，适合只允许直接回答的场景。 |
| `tool_allowlist: ["get_order"]` | Allow the named tool with any arguments. / 允许该工具，但不限制参数。 |
| `tool_allowlist: [{"tool": "get_order", "arguments": {"order_id": "123"}}]` | Allow only the exact tool-and-arguments pair. / 只允许工具名和参数都完全匹配的调用。 |

The allowlist is evaluated against every candidate `tool_call` event. It is a
scenario security boundary, not a replacement for business assertions,
relations, side-effect checks or tool-call counts:

白名单会检查候选 Trace 中的每一个 `tool_call` 事件。它是场景级安全边界，但不
替代业务断言、跨步骤关系、副作用检查或调用次数约束：

- use `tool_allowlist` to define which tools are in scope;
- use `tool_limits` to prevent missing, repeated or runaway calls;
- use `path_rules` to define valid sequences and safe extra observations;
- use `relations` and `side_effects` to prove the business meaning of results.

- 用 `tool_allowlist` 定义场景可以触碰哪些工具；
- 用 `tool_limits` 防止工具漏调用、重复调用或循环调用；
- 用 `path_rules` 定义合法调用顺序和安全的额外查询；
- 用 `relations` 与 `side_effects` 证明工具结果是否真正满足业务含义。

## Configuration / 配置

```json
{
  "final_answer_mode": "claims-only",
  "contract": {
    "tool_allowlist": [
      "get_order",
      {
        "tool": "check_refund_eligibility",
        "arguments": {"order_id": "123"}
      },
      {
        "tool": "refund_order",
        "arguments": {"order_id": "123", "amount": 88}
      }
    ],
    "tool_limits": [
      {"tool": "get_order", "min_calls": 1, "max_calls": 1},
      {"tool": "check_refund_eligibility", "min_calls": 1, "max_calls": 1},
      {"tool": "refund_order", "min_calls": 1, "max_calls": 1}
    ]
  }
}
```

The string form is shorthand for `{ "tool": "..." }`. An object with
`arguments` is an exact JSON object match; it is intentionally not a partial
subset match, so a newly added argument cannot silently pass the boundary.

字符串形式是 `{ "tool": "..." }` 的简写。带 `arguments` 的对象要求 JSON 参数对象
完全相等；它不是“只匹配部分字段”，因此 Agent 偷偷增加参数时不会静默通过。

## Observable evidence / 可观察证据

For an unauthorized call, the comparison report contains:

未授权调用会在比较报告中包含：

```json
{
  "category": "unauthorized_tool_call",
  "path": "tool_calls[2]",
  "baseline": [{"tool": "get_order"}],
  "candidate": {
    "type": "tool_call",
    "call_id": "call-3",
    "tool": "delete_order",
    "arguments": {"order_id": "123"}
  },
  "message": "tool call is not permitted by contract.tool_allowlist"
}
```

`path` is zero-based within the candidate tool-call list. The comparison fails
with a non-zero CLI exit code, so the same boundary can block a pull request.

`path` 是候选工具调用列表中的从零开始索引。比较会失败并返回非零 CLI 退出码，
因此这个边界可以直接阻断 Pull Request。

## Acceptance cases / 验收场景

The repository tests all of these cases:

仓库测试覆盖以下场景：

1. A missing allowlist keeps the old unrestricted behavior.
2. A named tool passes when its call matches.
3. An empty allowlist rejects every observed tool call.
4. A tool with mismatched arguments is rejected.
5. Unknown fields, invalid entry types and non-object arguments are rejected at config load time.
6. Compatibility detection recognizes an allowlist-only contract.
7. The refund business case allows exactly its three business tools and still catches duplicate refunds with `tool_count` and `step_limit`.

1. 省略白名单时保持旧的“不限制工具目录”行为；
2. 调用清单中的工具且匹配规则时通过；
3. 空白名单拒绝所有工具调用；
4. 工具参数不匹配时拒绝；
5. 配置加载阶段拒绝未知字段、错误条目类型和非对象参数；
6. 兼容性检查能够识别只有白名单的 Contract；
7. 退款案例只允许三个业务工具，并继续用 `tool_count` 与 `step_limit` 捕获重复退款。

Run the focused checks:

```bash
PYTHONPATH=src python3 -m unittest \
  tests.test_contracts \
  tests.test_migration \
  tests.test_refund_business_case -v
```

运行重点检查：

```bash
PYTHONPATH=src python3 -m unittest \
  tests.test_contracts \
  tests.test_migration \
  tests.test_refund_business_case -v
```

## Compatibility / 兼容性

This is an additive v4.9 Contract field. Existing configurations do not need
editing. The new field is serialized only when it was explicitly configured,
which preserves the distinction between “not configured” and “deny all”.

这是 v4.9 新增的 Contract 字段，不要求修改已有配置。只有显式配置时才会序列化
这个字段，从而保留“未配置”和“拒绝全部”之间的区别。

The allowlist does not authorize external side effects by itself. A production
integration must still enforce permissions in the actual tool gateway; this
framework verifies that the observed Agent behavior stayed within the declared
scenario boundary.

白名单本身不会给外部系统授予权限。生产接入仍必须在真实 Tool Gateway 中执行权限
控制；本框架负责验证 Agent 的实际行为是否始终处于场景声明的边界内。
