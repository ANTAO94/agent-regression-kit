# v4.6 acceptance / v4.6 验收

v4.6 addresses a common source of false positives: a valid Agent may add a
read-only lookup while preserving the required business steps. The release
adds explicit path matching modes instead of changing the default strict
behavior.

v4.6 解决一类常见误报：Agent 增加只读查询，但核心业务步骤没有改变。这个版本
通过显式路径模式支持这种变化，不修改默认的严格行为。

## Acceptance matrix / 验收矩阵

| Check / 检查 | Expected result / 预期结果 |
| --- | --- |
| Existing path contract without `mode` / 未配置 mode | keeps `exact` behavior; no migration |
| `ordered_subsequence` / 有序子序列 | allows extra calls while required rules stay ordered |
| `unordered_subset` / 无序子集 | requires every listed rule but permits order and extra calls |
| Reordered required steps / 必需步骤乱序 | exit `1`, `behavior_path` difference |
| Forbidden tool / 禁止工具 | exit `1`, `forbidden_tool` difference |
| Step limit / 步骤上限 | still blocks excessive calls |
| Unknown mode / 未知模式 | configuration validation exits `2` with a clear error |
| Full unit suite / 完整单测 | all tests pass |
| Dedicated CI workflow / 专用 CI | positive extra-query case passes; negative cases fail closed |

## Safety boundary / 安全边界

`ordered_subsequence` means that extra calls are allowed; it does not mean
that extra calls are trusted. Keep `must_not_call` for dangerous operations,
set `max_steps`, and use assertions, relations, side effects and structured
claims for business invariants. Use `unordered_subset` only where the domain
really permits reordering; it is not a general fallback for unstable tests.

`ordered_subsequence` 只表示允许额外调用，并不表示额外调用天然可信。危险操作仍要
配置 `must_not_call`，同时设置 `max_steps`，再用 assertions、relations、side_effects
和结构化 claims 保护业务不变量。只有业务上确实允许乱序时才使用
`unordered_subset`，不要把它当成消除不稳定测试的兜底开关。

The tolerant path matcher is deterministic and does not execute user code or
call an LLM judge. It checks the candidate Trace only. The comparator may skip
baseline result-list alignment when the candidate path has extra calls; add
explicit path-rule result checks or contract assertions when those extra
results are business-significant.

路径匹配是确定性的，不执行用户代码，也不调用 LLM Judge，只检查 candidate Trace。
当候选路径包含额外调用时，比较器不会强行把额外结果和 baseline 结果按位置对齐；
如果额外结果本身有业务意义，应在 path rule、assertion 或 relation 中显式写出。
