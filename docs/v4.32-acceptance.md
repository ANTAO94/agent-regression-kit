# v4.32 acceptance / v4.32 验收

## Scope / 范围

v4.32 adds a semantic binding layer on top of the v4.31 evidence index. A
study can now connect a controlled JSON field in an indexed descriptor to one
of the provenance values that identifies the recorded Agent run. This closes a
narrow but important gap: a descriptor may be unchanged and its SHA-256 may be
correct while still describing the wrong input, tool schema or adapter.

v4.32 在 v4.31 evidence index 之上增加语义绑定层。study 可以把已索引描述文件中的受控 JSON
字段，与标识本次 Agent 运行的 provenance 值关联起来。它补上一个明确缺口：描述文件可能没有被
修改、SHA-256 也正确，但实际描述的却是错误的 input、tool schema 或 adapter。

This remains an explicit provenance check, not a general truth oracle. The
framework only checks the fields and targets declared by the manifest; it does
not decide whether the provenance or descriptor is truthful, representative or
complete.

这仍然是显式的来源一致性检查，不是通用真实性裁判。框架只检查 manifest 声明的字段和 target，
不会判断 provenance 或描述文件本身是否真实、具有代表性或覆盖完整。

## Manifest / manifest 格式

The v4.31 `evidence` index remains the file-identity boundary. v4.32 adds
`evidence_bindings` and two integrity controls:

v4.31 的 `evidence` index 继续负责文件身份边界。v4.32 增加 `evidence_bindings` 和两个完整性策略字段：

```json
{
  "provenance": {
    "provider": "fixture-provider",
    "model": "fixture-model-v1",
    "input_sha256": "<input-sha256>",
    "tool_schema_sha256": "<tool-schema-sha256>",
    "adapter": "recorded-trace-import"
  },
  "evidence": [
    {
      "id": "input-descriptor",
      "role": "input",
      "path": "evidence/input.json",
      "sha256": "<file-sha256>"
    },
    {
      "id": "adapter-descriptor",
      "role": "adapter",
      "path": "evidence/adapter.json",
      "sha256": "<file-sha256>"
    }
  ],
  "evidence_bindings": [
    {
      "evidence_id": "input-descriptor",
      "target": "provenance.input_sha256",
      "field": "input_sha256"
    },
    {
      "evidence_id": "adapter-descriptor",
      "target": "provenance.adapter",
      "field": "adapter"
    }
  ],
  "integrity": {
    "require_evidence_index": true,
    "required_evidence_roles": ["input", "adapter"],
    "require_evidence_bindings": true,
    "required_evidence_bindings": [
      "provenance.input_sha256",
      "provenance.adapter"
    ]
  }
}
```

Supported targets and their required roles/fields are:

| Target | Required role | Required descriptor field |
| --- | --- | --- |
| `provenance.input_sha256` | `input` | `input_sha256` |
| `provenance.tool_schema_sha256` | `tool_schema` | `tool_schema_sha256` |
| `provenance.adapter` | `adapter` | `adapter` |

The binding must reference an indexed evidence ID. The evaluator first checks
the evidence file SHA-256, parses the descriptor as a JSON object and compares
only the declared field with the provenance value. It never copies the
descriptor object into the report.

支持的 target、必需 role 和字段如下：

| Target | 必需 role | 描述文件必需字段 |
| --- | --- | --- |
| `provenance.input_sha256` | `input` | `input_sha256` |
| `provenance.tool_schema_sha256` | `tool_schema` | `tool_schema_sha256` |
| `provenance.adapter` | `adapter` | `adapter` |

绑定必须引用已进入 evidence index 的 ID。评估器先校验 evidence 文件 SHA-256，再把描述文件解析为
JSON 对象，只比较声明字段与 provenance 值；描述文件对象本身不会被写入报告。

## Report / 报告

Successful reports add a content-free summary:

成功报告增加不含原文的摘要：

```json
{
  "evidence_bindings": {
    "required": true,
    "verified": true,
    "binding_count": 2,
    "targets": [
      "provenance.adapter",
      "provenance.input_sha256"
    ],
    "bindings": [
      {
        "evidence_id": "input-descriptor",
        "target": "provenance.input_sha256",
        "field": "input_sha256"
      }
    ]
  },
  "evidence_integrity": {
    "evidence_bindings_required": true,
    "evidence_bindings_verified": true
  }
}
```

The report contains IDs, targets and fields only. A missing indexed ID, wrong
role, unsupported target, missing required target, invalid descriptor JSON or
semantic mismatch is invalid evidence and the CLI returns status `2` before
Contract/Stability evaluation.

报告只包含 ID、target 和 field。缺少索引 ID、role 错误、target 不支持、缺少必需 target、描述文件
不是合法 JSON 或语义不一致，都属于无效证据；CLI 会在 Contract/Stability 评估前返回状态 `2`。

## Example and CI / 示例与 CI

The project-owned deterministic example now writes matching descriptor fields
and requires all three supported bindings:

项目自带确定性示例现在会写入匹配的描述字段，并要求三个受支持的绑定全部存在：

```bash
python examples/sampling-study/create_demo_study.py \
  --out-dir work/order-123-study
agent-regression study \
  --manifest work/order-123-study/study.json \
  --format markdown \
  --out work/order-123-study/report.md
```

Core CI verifies three evidence boundaries in copied temporary bundles:

1. changing a run Trace fails the file hash check;
2. changing a descriptor without refreshing its index hash fails the evidence index;
3. changing a descriptor and refreshing its index hash still fails the semantic binding.

核心 CI 在复制出的临时 bundle 中验证三层边界：修改 run Trace 会触发文件哈希失败；只修改描述文件
会触发 evidence index 失败；修改描述文件并同步刷新 index 哈希后，仍会触发语义绑定失败。

## Local acceptance / 本地验收

The v4.32 source tree passes **285 tests** with `PYTHONPATH=src`. Focused
coverage includes v4.31 evidence-index compatibility, required binding targets,
role/field validation, hash-refresh semantic mismatch, descriptor redaction
boundaries, deterministic study generation and CI workflow assertions.

v4.32 源码树在 `PYTHONPATH=src` 下通过 **285 项测试**。专项覆盖 v4.31 evidence index 兼容、必需
binding target、role/field 校验、刷新哈希后的语义错配、描述文件报告边界、确定性 study 生成和 CI
工作流断言。

## Compatibility and boundaries / 兼容与边界

- v4.31 and earlier manifests without `evidence_bindings` remain valid.
- Enabling `require_evidence_bindings` also requires `require_evidence_index`.
- Bindings are limited to three explicit provenance targets; this is deliberate
  to keep the report and parser small and auditable.
- The layer is not a cryptographic signature, a provider attestation or a
  semantic correctness proof.

- 不带 `evidence_bindings` 的 v4.31 及更早 manifest 继续兼容。
- 开启 `require_evidence_bindings` 时必须同时开启 `require_evidence_index`。
- 绑定范围刻意限制为三个明确 provenance target，保持报告和解析器小而可审计。
- 这不是密码学签名、供应商证明或业务语义正确性证明。
